## 1. Executive summary

Model Change Review Lab is currently a React 19 + TypeScript + Vite application. Its domain layer contains a deterministic 24-month financial model, typed assumption and proposal structures, validation, atomic transaction helpers, a reducer-based client state tree, proposal variants, impact comparison, traceability, history, reset, and undo. The proposal provider is deterministic and local; no real LLM is involved. The deployed frontend already exists and must not be redeployed as part of this task.

This project increment adds a real backend and persistence layer:

- **Frontend:** React + TypeScript + Vite, retained.
- **API:** Python 3.12+, FastAPI, Pydantic, SQLAlchemy 2.x, Alembic.
- **Database:** PostgreSQL 16 for local development and CI.
- **Canonical server state:** current assumptions, baseline, revision, proposal workspaces/variants, and transaction history.
- **Canonical calculations:** continue to live only in `src/domain/calculation.ts` in TypeScript. The backend persists assumptions and validates/apply operations but does not implement revenue, payroll, EBITDA, ending-cash, cumulative-revenue, or trace formulas.
- **Proposal generation:** move the existing three deterministic proposal presets to the backend. This is still a simulated proposal provider, not an LLM integration.
- **Concurrency:** session-row locking, expected-revision checks, stale proposal rejection, and request idempotency.
- **Testing:** Python unit/API/integration tests against real PostgreSQL, existing Vitest tests, and Playwright tests covering the frontend-to-API-to-PostgreSQL path.

The resulting application must let a user generate a proposal, edit or duplicate variants, inspect impact using the existing TypeScript calculation engine, accept a valid variant, reload and recover persisted state, inspect history, and undo an eligible transaction. A stale proposal or duplicate request must never overwrite or double-apply a newer commit.

## 2. Product goals

### 2.1 Primary goals

1. Introduce a maintainable FastAPI service integrated with the existing frontend.
2. Persist session-scoped model state, immutable baseline, proposal workspace/variant state, and committed transaction history in PostgreSQL.
3. Make server-side revision checks and database transactions authoritative for all persisted model mutations.
4. Preserve the existing product experience and calculation logic instead of rewriting the app.
5. Prove end-to-end correctness with automated tests, including stale revisions, duplicate requests, transactional rollback, and concurrent updates.
6. Provide reproducible local setup, database migrations, API documentation, and CI validation.
7. Audit the existing state-safety/race issues and public claims as part of implementation, correcting confirmed defects and unsupported claims rather than copying prior audit conclusions blindly.

### 2.2 Success measures

The implementation is accepted only when all mandatory criteria below pass:

- [ ] A fresh anonymous session starts with the existing synthetic baseline and revision `1`.
- [ ] The session is isolated from other sessions; no user can access another session without its high-entropy bearer token.
- [ ] A model edit is validated by the API, committed atomically, persisted, and returned with a new revision.
- [ ] All three existing proposal presets are generated by the API using a precise baseline snapshot.
- [ ] Proposal workspace/variant changes survive page reloads.
- [ ] Proposal impact and financial metrics are still computed by the existing TypeScript engine, not by a duplicate Python formula engine.
- [ ] A proposal based on revision `r` cannot be accepted if the canonical revision is no longer `r`.
- [ ] A successful accept changes the model, increments revision exactly once, closes the workspace as accepted, and records full provenance in one database transaction.
- [ ] Repeating an identical mutation with the same idempotency key returns the original response without repeating the mutation.
- [ ] Reusing an idempotency key with a different method/path/body returns `409` and changes nothing.
- [ ] Undo restores the previous assumptions, increments revision, and records an undo event without deleting historical records.
- [ ] Reset-to-baseline is persisted and represented in history when it changes the model.
- [ ] Python tests run against a real PostgreSQL service in CI; frontend unit and E2E tests continue to run.
- [ ] Setup and test commands are documented and verified by the agent.
- [ ] No commit, push, or deployment is performed by the agent.

### 2.3 Non-goals

Do not implement any of the following in this task:

- Real LLM/agent integration, model-provider APIs, prompt execution, or API keys.
- Authentication providers, accounts, login, organization/workspace sharing, or user profiles.
- Multi-tenant collaboration, WebSockets, presence, live cursors, or background jobs.
- A Python implementation of the financial calculation/trace engine.
- New finance formulas or model-semantic changes.
- A new frontend framework, UI redesign, state-management library, or complete rewrite.
- Redis, a message queue, microservices, Kubernetes, Terraform, or elaborate deployment infrastructure.
- Changes to the current hosted deployment, DNS, hosting settings, secrets, environment variables in hosting dashboards, or production database provisioning.
- Claims that this is production-ready or enterprise-compliant. This is a portfolio-grade, synthetic-data demonstration.

### 3.4 Source-of-truth rules

- The server is allowed to validate assumptions and apply a whitelisted set of assumption operations to a cloned snapshot. Applying input edits is not a reason to duplicate derived financial formulas.
- Never trust client-provided `previousValue`, `targetKey`, `targetPeriod`, `displayUnit`, `changeLabel`, `baseAssumptions`, `baseRevision`, or transaction snapshots for a mutation. - Never use the current working model as the base of an old proposal. A workspace stores an immutable `baseAssumptions` snapshot and `baseRevision` at generation time.

## 5. Anonymous session isolation and security

This app has no sign-in. It must not store every visitor's model in one shared database row.

### 5.1 Capability-token design

1. On browser startup, read `localStorage['mcrl.workspace-token.v1']`.
2. If absent, create a high-entropy 32-byte token using `crypto.getRandomValues`, encode it as base64url, and synchronously save it in localStorage before making a request.
3. Send it as `X-Workspace-Token` to `POST /api/v1/session`.
4. The backend hashes the token with SHA-256 and stores only the hex digest in `demo_sessions.token_hash`. Never store or log the raw token.
5. `POST /api/v1/session` creates a new synthetic-data session if the hash does not exist, or returns the existing session if it does. Make this upsert race-safe so simultaneous browser tabs with the same token converge on one session.
6. All other API endpoints require the same `X-Workspace-Token` header. Resolve the hash to a session on the server. Every database query for state/workspaces/history must be scoped to the resolved `session_id`.
7. If the token is absent/invalid on a non-session route, return `401`. If an object belongs to another session, return `404` without revealing whether it exists.
8. If a token's session has been inactive for more than **30 days**, `POST /api/v1/session` expires the old session, creates a fresh baseline session, and returns it. The response must make `sessionResetBecauseExpired: true` so the frontend can inform the user that the demo workspace was reset. Other routes do not silently resurrect expired sessions; they return `401` and the client reinitializes through the session endpoint.

This token is a bearer capability, not identity authentication. Document that anyone possessing the token can access that anonymous demo workspace. The system stores synthetic data only, so no user/customer/financial confidential data may be added.

### 5.2 CORS and transport

- Configure `CORS_ORIGINS` as a comma-separated explicit allowlist.
- Local default: `http://localhost:5173,http://127.0.0.1:5173,http://localhost:4173,http://127.0.0.1:4173`.
- Never use wildcard `*` for allowed origins.
- Allow methods `GET, POST, PATCH, DELETE, OPTIONS` only.
- Allow headers `Content-Type, X-Workspace-Token, Idempotency-Key` only.
- Do not use cookies, server sessions, or `Access-Control-Allow-Credentials`.
- Deployment must use HTTPS, but the agent must not make deployment changes in this task.

### 5.3 Request limits and safe errors

- Limit `limit` query parameters to `1..100`; default history/workspace list limit is 50.
- Limit proposal workspaces to one active workspace per session and at most three variants in that workspace.
- Limit each proposal variant to at most 24 operations; the current presets use 18 or 21.
- A workspace must contain at least one variant. A variant's targets are fixed by the original generated template; the API lets the user edit proposed values but not change operation targets or add arbitrary operations.
- Use generic `500` responses for unexpected failures and log the full traceback server-side without tokens or request bodies that could contain the token. Do not expose exception messages, SQL, or secrets to the client.
- Validate `Origin` where provided against configured CORS origins for mutation routes, but do not treat Origin validation as authentication.
- Do not rely on CORS alone for authorization; authorization comes from the workspace bearer token and per-session database scoping.

## 6. Database schema

Use SQLAlchemy models plus an initial Alembic migration. PostgreSQL constraints/indexes must enforce structural invariants when they can be expressed in SQL; service-level checks alone are not enough for unique ownership/idempotency invariants.

### 6.1 `demo_sessions`

Fields:

- `id UUID PRIMARY KEY`
- `token_hash CHAR(64) NOT NULL UNIQUE`
- `baseline_assumptions JSONB NOT NULL`
- `working_assumptions JSONB NOT NULL`
- `revision INTEGER NOT NULL DEFAULT 1 CHECK (revision >= 1)`
- `created_at TIMESTAMPTZ NOT NULL`
- `updated_at TIMESTAMPTZ NOT NULL`
- `last_seen_at TIMESTAMPTZ NOT NULL`

The baseline is immutable after session creation. The service must never update it during edits, accept, undo, or reset.

### 6.2 `proposal_workspaces`

Fields:

- `id UUID PRIMARY KEY`
- `session_id UUID NOT NULL REFERENCES demo_sessions(id) ON DELETE CASCADE`
- `source_template_id TEXT NOT NULL` constrained to the three template IDs
- `title TEXT NOT NULL`
- `description TEXT NOT NULL`
- `base_revision INTEGER NOT NULL CHECK (base_revision >= 1)`
- `base_assumptions JSONB NOT NULL`
- `status TEXT NOT NULL CHECK (status IN ('active','accepted','rejected','archived','dismissed'))`
- `selected_variant_id UUID NOT NULL`
- `comparison_variant_ids JSONB NOT NULL`
- `accepted_variant_id UUID NULL`
- `created_at TIMESTAMPTZ NOT NULL`
- `updated_at TIMESTAMPTZ NOT NULL`
- `closed_at TIMESTAMPTZ NULL`

Create a **partial unique index** enforcing at most one row with `status='active'` per `session_id`. An active workspace remains active but becomes stale when `base_revision != demo_sessions.revision`. It stays inspectable until it is accepted, rejected, archived, or dismissed. Do not silently overwrite it with a new workspace.

### 6.3 `proposal_variants`

Fields:

- `id UUID PRIMARY KEY`
- `workspace_id UUID NOT NULL REFERENCES proposal_workspaces(id) ON DELETE CASCADE`
- `label TEXT NOT NULL`
- `source_template_id TEXT NOT NULL` constrained to the same three template IDs
- `duplicated_from_variant_id UUID NULL`
- `operations JSONB NOT NULL`
- `reset_snapshot_operations JSONB NOT NULL`
- `created_at TIMESTAMPTZ NOT NULL`
- `updated_at TIMESTAMPTZ NOT NULL`
- `is_original BOOLEAN NOT NULL DEFAULT FALSE`

Create a partial unique index allowing at most one `is_original=true` variant per workspace. The original generated variant is marked true and may not be deleted, matching the current UI behavior. The workspace must always have at least one variant. The source template and target set for a variant are immutable; only each existing operation's `proposedValue` may change. The reset snapshot is immutable after variant creation. When a variant is duplicated, clone the source variant's **current operations** into the new variant's `operations` and also clone those same current operations into the new variant's `resetSnapshotOperations`. This means reset restores a copy to the values it had when it was duplicated, even if the source was edited before duplication.

### 6.4 `change_transactions`

Fields:

- `id UUID PRIMARY KEY`
- `session_id UUID NOT NULL REFERENCES demo_sessions(id) ON DELETE CASCADE`
- `resulting_revision INTEGER NOT NULL CHECK (resulting_revision >= 2)`
- `kind TEXT NOT NULL CHECK (kind IN ('manual-edit','proposal-accepted','reset-to-baseline','undo'))`
- `description TEXT NOT NULL`
- `affected_cell_ids JSONB NOT NULL`
- `previous_assumptions JSONB NOT NULL`
- `new_assumptions JSONB NOT NULL`
- `provenance JSONB NULL`
- `undoes_transaction_id UUID NULL REFERENCES change_transactions(id) ON DELETE SET NULL`
- `undone_by_transaction_id UUID NULL REFERENCES change_transactions(id) ON DELETE SET NULL`
- `created_at TIMESTAMPTZ NOT NULL`

Add unique constraint `(session_id, resulting_revision)`. A transaction row is an immutable historical event except that a forward transaction's `undone_by_transaction_id` can be set once when it is undone. Do not delete historical rows during undo or reset.

`provenance` for `proposal-accepted` must contain `proposalWorkspaceId`, `variantId`, `variantLabel`, `sourceTemplateId`, and `baseRevision`. For `manual-edit`, it may be null. For `reset-to-baseline` and `undo`, it may identify the original transaction being undone/reset target as appropriate; never fabricate proposal provenance.

`affected_cell_ids` contains input-setting/assumption cell IDs that differ between `previous_assumptions` and `new_assumptions`. Derived calculated cells must not be persisted as editable targets. Use deterministic ordering.

### 6.5 `idempotency_requests`

Fields:

- `id UUID PRIMARY KEY`
- `session_id UUID NOT NULL REFERENCES demo_sessions(id) ON DELETE CASCADE`
- `idempotency_key VARCHAR(128) NOT NULL`
- `method TEXT NOT NULL`
- `path TEXT NOT NULL`
- `request_hash CHAR(64) NOT NULL`
- `response_status INTEGER NOT NULL`
- `response_body JSONB NOT NULL`
- `created_at TIMESTAMPTZ NOT NULL`
- unique `(session_id, idempotency_key)`

For a successful mutating request, persist the idempotency record in the same transaction as the requested mutation. On replay with the same key and exact method/path/request hash, return the stored response status/body and do not repeat the action. If the key already exists with a different method/path/body hash, return `409 idempotency_key_reused`; do not mutate state. Do not store bearer tokens in this table. Do not cache unsuccessful validation/conflict responses as if they committed successfully.

## 7. Canonical model state and mutation semantics

### 7.1 Revision model

- New session starts at revision **1**.
- The baseline snapshot never changes.
- Every successful canonical model mutation that changes the model increments revision by exactly one.
- Mutations that are rejected, invalid, stale, duplicate, or idempotent replays do not increment revision again.
- `reset-to-baseline` when the model already equals baseline is an idempotent no-op: return `changed: false`, do not create a transaction, and do not increment revision.
- Editing a field to its current value is also a no-op: return `changed: false`, no transaction, no revision change.
- Proposal workspace changes (generation, variant duplicate/edit/remove/reset, selection, reject/archive/dismiss) do not change the model revision.
- An active proposal is stale exactly when `workspace.baseRevision !== session.revision`. Staleness is derived; do not update `baseRevision` when the model changes.

### 7.2 Atomic commit sequence

For manual edit, proposal acceptance, reset, and undo:

1. Validate request structure.
2. Begin database transaction.
3. Lock the `demo_sessions` row with `SELECT ... FOR UPDATE`.
4. Check idempotency key replay before checking the current revision. If the same successful request was previously committed, return its saved response.
5. Compare request `expectedRevision` with the locked session revision. If different, return `409 revision_conflict` and do not mutate.
6. Load all related resources using both resource ID and the authorized `session_id`.
7. Validate target/operation sets and business invariants using server-owned values.
8. Clone the current assumption JSON into an in-memory draft, apply all operations, and validate the complete resulting assumptions object.
9. If any operation fails, write nothing and roll back the transaction.
10. Persist the new assumptions and new revision, transaction history row(s), related workspace status if applicable, and the idempotency success response in the same SQL transaction.
11. Commit.
12. Return the canonical server snapshot/response; do not optimistically declare success before this response.

Every endpoint that writes canonical model state follows this sequence. A database failure halfway through a commit must leave the session revision, model, history, workspace status, and idempotency table unchanged.

### 7.3 Safe target parsing

The request's `targetCellId` must be parsed against an explicit allowlist:

- `setting:startingRevenueUsd`
- `setting:startingCashUsd`
- `assumption:revenueGrowthRate:M01` through `...:M24`
- `assumption:engineeringFte:M01` through `...:M24`
- `assumption:otherFte:M01` through `...:M24`
- `assumption:loadedMonthlyCostPerFteUsd:M01` through `...:M24`
- `assumption:otherOperatingExpenseUsd:M01` through `...:M24`

Month strings are strictly zero-padded (`M01`…`M24`). Reject any `calculated:*` cell ID, invalid period, unsupported key, extra colon segment, or target metadata that does not match the parsed target. A user cannot change a proposal's target by editing its payload.

For each accepted operation, generate canonical operation metadata on the server:

- `targetKey` and `targetPeriod` from the parsed cell ID.
- `previousValue` from the proposal's immutable base assumptions (for variant display/metadata); before commit, because the revision matches, this must also equal the current canonical value.
- `proposedValue` from the validated request.
- `targetCellId` from the parsed ID.
- `displayUnit`: `percent` for growth, `fte` for engineering/other FTE, `usd` otherwise.
- `changeLabel`: deterministic label derived from field and month; never accept it from the client.

Reject duplicate target IDs in any operation set. The API must ensure an operation set is all-or-nothing.

## 8. API contract

All routes except `GET /health` require `X-Workspace-Token`, including `POST /api/v1/session`. All POST/PATCH/DELETE routes require an `Idempotency-Key` header of 8–128 characters. Each response uses camelCase property names.

### 8.1 Standard error envelope

All error responses use this shape:

```json
{
  "error": {
    "code": "revision_conflict",
    "message": "The model changed since this action was prepared.",
    "details": {
      "expectedRevision": 3,
      "currentRevision": 4
    },
    "requestId": "uuid"
  }
}
```

`details` may be omitted. Never return a traceback or SQL internals.

Use these status/code mappings:

| HTTP | Error code | When |
|---:|---|---|
| 400 | `invalid_request` | Invalid query/header syntax not covered by schema validation. |
| 401 | `invalid_workspace_token` | Token missing, malformed, unknown, or expired on a non-session route. |
| 404 | `resource_not_found` | Workspace/variant/transaction is absent or does not belong to the caller's session. |
| 409 | `revision_conflict` | A mutation's expected revision is not current. |
| 409 | `stale_proposal` | Acceptance was requested for a workspace whose base revision is stale. |
| 409 | `active_workspace_exists` | Attempt to generate while an active workspace exists. |
| 409 | `workspace_not_active` | Attempt to mutate/accept a workspace that is already closed. |
| 409 | `variant_limit_reached` | Attempt to create a fourth variant. |
| 409 | `last_variant_required` | Attempt to remove the final variant. |
| 409 | `original_variant_required` | Attempt to remove the original generated variant. |
| 409 | `nothing_to_undo` | No eligible committed transaction remains to undo. |
| 409 | `idempotency_key_reused` | A key was replayed with different method/path/body. |
| 409 | `duplicate_acceptance` | Workspace/variant was already accepted; never reapply it. |
| 422 | `validation_error` | Field/operation/model validation failed. |
| 422 | `proposal_generation_invalid` | A generated preset would violate the model's allowed ranges. |
| 503 | `database_unavailable` | Database readiness/query failure prevented safe processing. |
| 500 | `internal_error` | Unexpected failure, with generic public message only. |

If Pydantic raises request validation errors, map them to this same error envelope with code `validation_error`; do not expose FastAPI's default inconsistent raw error array.

### 8.3 Create/resume session

`POST /api/v1/session`

Headers: `X-Workspace-Token`, `Idempotency-Key` is **not required** for this route because the token hash is its idempotency identity.

No request body.

Behavior:

- Hash and validate the high-entropy token.
- If a live session exists, update `lastSeenAt` and return it.
- If a session exists but has been inactive for more than 30 days, delete the expired session and its cascaded data, create a new seeded session, and set `sessionResetBecauseExpired: true`.
- If no session exists, create a seeded session and set `sessionResetBecauseExpired: false`.
- Make concurrent initialization with the same token hash safe: only one session may be created.

Response shape:

```json
{
  "sessionId": "uuid",
  "sessionResetBecauseExpired": false,
  "baselineAssumptions": { "startingRevenueUsd": 750000, "startingCashUsd": 3000000, "months": [] },
  "workingAssumptions": { "startingRevenueUsd": 750000, "startingCashUsd": 3000000, "months": [] },
  "revision": 1,
  "activeWorkspace": null,
  "archivedWorkspaces": [],
  "changeHistory": [],
  "canUndo": false
}
```

The `months` array in real responses contains all 24 periods. The abbreviated array above is illustrative only.

The raw token is provided by the client, not returned by the server. The session endpoint does not persist caller-supplied model data.

### 8.8 Generate proposal workspace

`POST /api/v1/proposals`

Headers: `Idempotency-Key`.

Request:

```json
{
  "templateId": "hire-engineers-from-q3",
  "expectedRevision": 1
}
```

Allowed template IDs: exactly the three in §3.3.

Behavior:

1. Lock the session row and apply idempotency handling.
2. Require `expectedRevision` to match current revision.
3. Reject if any workspace with status `active` already exists.
4. Copy current assumptions and current revision into immutable workspace base fields.
5. Generate canonical operations using the selected deterministic preset, validate them all against the copied base, and fail without creating a workspace if any generated value is out of range.
6. Create a workspace UUID and one original variant UUID. Variant label is `Original proposal`. Store its operations as both `operations` and `resetSnapshotOperations`.
7. Set `selectedVariantId` to this variant ID and `comparisonVariantIds` to `[variantId]`.
8. Set workspace status to `active` and persist all records in one transaction.
9. Return `{"workspace": <workspace DTO>, "revision": n}`.

An API request that loses a race to another generation or model mutation returns the corresponding `409` with no duplicate workspace. Proposal creation does not increment model revision.

### 8.15 Accept a proposal variant

`POST /api/v1/proposals/{workspaceId}/accept`

Headers: `Idempotency-Key`.

Request:

```json
{
  "variantId": "uuid",
  "expectedRevision": 1
}
```

Behavior:

1. Lock and authorize the session, workspace, and variant.
2. Apply idempotency replay logic.
3. If the workspace is already accepted, return `409 duplicate_acceptance`; do not write or increment revision.
4. Require workspace status `active`.
5. Require both request `expectedRevision` and workspace `baseRevision` to equal the current session revision. Otherwise return `409 stale_proposal` or `409 revision_conflict` with expected/current/base revision values; no changes.
6. Regenerate/validate operation metadata from server-stored base and variant `proposedValue`s. Reject empty, duplicate, invalid, or tampered operation sets.
7. Confirm each operation's original value from the stored base is identical to the current canonical value. This must hold whenever the revision guard passes; if not, fail closed with `409 stale_proposal` and log the invariant violation.
8. Apply operations to a clone of canonical working assumptions. Do not calculate derived finance values in Python.
9. Persist new assumptions, incremented revision, a `proposal-accepted` transaction with full previous/new snapshots and required provenance, workspace status `accepted`, `acceptedVariantId`, `closedAt`, and idempotency response in one database transaction.
10. Return the complete session snapshot and accepted workspace ID/variant ID.

No frontend acceptance path may update canonical state before the API commits. On success, the frontend hydrates from the returned server snapshot and recalculates derived values using the TypeScript engine.

### 8.16 Reject, archive, and dismiss workspace

- `POST /api/v1/proposals/{workspaceId}/reject` — reject an active, non-stale workspace. Set status `rejected`, set `closedAt`, retain variants and base snapshot for audit/listing. It does not change model revision.
- `POST /api/v1/proposals/{workspaceId}/archive` — archive an active workspace only when it is stale. Set status `archived`, set `closedAt`, retain it for the archived-workspace list.
- `POST /api/v1/proposals/{workspaceId}/dismiss` — dismiss an active stale workspace without adding it to the archived-workspace list. Set status `dismissed`, set `closedAt`, retain its row and variants in PostgreSQL until session expiry.

All require `Idempotency-Key`. No method deletes historical workspace/variant records before session expiration. Rejecting an active but stale workspace must use archive/dismiss, not `reject`; return `409 stale_proposal` if `reject` is called on a stale workspace. Any closed workspace cannot be accepted or edited.

### 8.18 Undo last eligible transaction

`POST /api/v1/undo`

Headers: `Idempotency-Key`.

Request:

```json
{"expectedRevision": 3}
```

Behavior:

1. Lock session and apply idempotency replay handling.
2. Require expected revision to match current revision.
3. Select the most recent forward transaction in this session whose `kind` is one of `manual-edit`, `proposal-accepted`, or `reset-to-baseline` and whose `undoneByTransactionId` is null, ordered by `resultingRevision DESC`.
4. If none exists, return `409 nothing_to_undo`.
5. Restore the selected transaction's exact `previousAssumptions` snapshot into current working state. Validate the restored assumptions object before persistence.
6. Create an `undo` transaction with previous assumptions equal to the current state, new assumptions equal to the restored state, `undoesTransactionId` pointing to the target, affected cell IDs derived from the diff, `resultingRevision = currentRevision + 1`, and a descriptive timestamp.
7. Set the target transaction's `undoneByTransactionId` to the undo transaction ID.
8. Persist restored assumptions, incremented revision, both history changes, and idempotency response atomically.
9. Return the complete session snapshot.

Undo never deletes or rewrites the old record's before/after snapshots or revision. Undo itself is a historical event and is not an undo target. If an active proposal exists, the successful undo makes it stale; it remains inspectable and cannot be accepted.

### 11.7 Playwright E2E tests

Use a real frontend preview, real FastAPI instance, and real PostgreSQL in the E2E test environment. Do not mock the backend for the critical persistence path.

Mandatory end-to-end cases:

1. Fresh session loads baseline values and revision.
2. Generate each preset; the workspace uses a server-generated baseline snapshot.
3. Duplicate and edit a variant; confirm the original is unchanged.
4. Reload the page and confirm the active workspace and variant edits persist.
5. Accept a valid proposal and verify the visible model updates, revision changes, and provenance appears in history.
6. Reload and verify accepted model/history persist and workspace is no longer active.
7. Direct edit, reload, and verify persistence.
8. Reset to baseline through the existing confirmation dialog; verify values are actually restored, not merely that the dialog closes.
9. Undo a committed change and verify actual assumption values restore and history contains an undo event.
10. Generate a proposal, edit the canonical model in a separate API call/tab, then attempt acceptance; verify the server rejects it as stale, model state is not changed by acceptance, and the UI presents the stale workspace.
11. Replay a successful accept with the same idempotency key through an API test; assert no double application.
12. Verify one anonymous token cannot read or mutate another session.
13. Verify all important requests target the configured API and no third-party AI service is called.

The current E2E suite must also be corrected where its comments claim stale guard/reset proof without asserting actual state. Do not describe a test as covering an invariant unless its body asserts the invariant.
